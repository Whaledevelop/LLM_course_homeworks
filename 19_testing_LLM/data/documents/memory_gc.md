# Управляемая память и Garbage Collector в Unity

## Managed heap

C#-код в Unity использует управляемую память. Объекты ссылочных типов, включая экземпляры обычных классов, массивы и строки, обычно размещаются в managed heap — управляемой куче. Локальная переменная ссылочного типа хранит ссылку на объект, а не все данные этого объекта.

Выделение памяти в управляемой куче называют managed allocation. Примеры операций, которые могут создавать такие выделения: создание объекта через `new`, создание массива, формирование новой строки и упаковка значения значимого типа в `object` или интерфейс.

Значимые типы не всегда размещаются только на стеке. Место хранения зависит от контекста: поле-структура может находиться внутри объекта в куче, а упаковка структуры создаёт отдельный управляемый объект.

## Работа Garbage Collector

Garbage Collector, или GC, освобождает управляемые объекты, которые больше недостижимы по ссылкам из работающей программы. Разработчик не освобождает такие объекты вручную аналогом `free`. Наличие ссылки на объект сохраняет его достижимым и не позволяет сборщику считать его мусором.

Сборка мусора требует процессорного времени. Unity может выполнять её инкрементально, разделяя часть работы между несколькими кадрами, если включён Incremental Garbage Collection. Инкрементальный режим уменьшает длительность отдельных пауз, но не устраняет стоимость выделения памяти и самой сборки.

`System.GC.Collect` запрашивает принудительную сборку. Такой вызов сам требует времени и не отменяет необходимость контролировать источники выделений. Обычный код не должен считать момент автоматической сборки детерминированным.

## Временные allocations

Временный объект может быстро потерять все ссылки, но память под него всё равно сначала выделяется. Если такой код работает каждый кадр, объём мусора постоянно растёт. После накопления мусора GC выполняет дополнительную работу, что может увеличить время кадра и вызвать заметный скачок времени выполнения.

Источниками временных выделений могут быть конкатенация строк, создание новых коллекций и массивов, замыкания с захватом переменных, упаковка значений и некоторые операции LINQ. Конкретное наличие allocation зависит от используемого API, реализации и версии среды, поэтому его проверяют измерением.

## Контроль выделений

Unity Profiler показывает маркер `GC.Alloc` для управляемых выделений, обнаруженных в профилируемом коде. Колонка выделенной памяти и модуль Memory помогают найти кадры и методы, создающие мусор.

Повторное использование уже созданных буферов и коллекций уменьшает число временных объектов. Для некоторых API Unity предоставляет варианты без выделения нового массива, например физические запросы с суффиксом `NonAlloc`, принимающие заранее созданный буфер результатов.

Управляемая память отличается от нативной памяти Unity. Уничтожение `GameObject`, текстуры или другого `UnityEngine.Object` и освобождение управляемой оболочки относятся к связанным, но не тождественным операциям. GC отвечает именно за управляемые объекты и не заменяет предусмотренное Unity уничтожение нативных объектов.
